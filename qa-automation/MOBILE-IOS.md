# Customer Mobile QA — iOS / Maestro

The milestone-1 suite uses the dedicated `qa-production` Expo build
(`com.enatega.multivendor.qa`) against the explicitly configured production
GraphQL endpoint. The app name is `Enatega QA • PROD`, so it cannot be confused
with the customer production app.

Validated toolchain on 2026-08-28:

- OpenJDK 17.0.20.1 (Maestro is always launched with this JDK)
- Maestro CLI 2.9.0
- Xcode 26.6 (Build 17F113)
- iOS Simulator runtime 26.5

## One-time workstation setup

```sh
brew install openjdk@17
brew tap mobile-dev-inc/tap
brew install mobile-dev-inc/tap/maestro
xcodebuild -downloadPlatform iOS
```

Verify and boot an available simulator:

```sh
export PATH="/opt/homebrew/opt/openjdk@17/bin:/opt/homebrew/bin:$PATH"
export JAVA_HOME="/opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home"
java -version
maestro --version
xcode-select -p
xcodebuild -version
xcrun simctl list devices available
xcrun simctl boot "iPhone 17 Pro"
open -a Simulator
```

## Build and install the QA app

Expo Go is not supported. From `enatega-multivendor-app`, install dependencies
and build the native simulator app:

```sh
npm ci
EXPO_PUBLIC_APP_ENV=qa-production npx expo run:ios --device "iPhone 17 Pro"
```

`expo run:ios` misidentifies a simulator UDID as a physical device under Xcode 26
(Expo SDK 53 cannot parse its `devicectl` output) and then fails demanding code
signing. Build the simulator slice directly instead — this is also what the
automation uses, because a Release build embeds the JS bundle and therefore needs
no Metro server while the flows run:

```sh
EXPO_PUBLIC_APP_ENV=qa-production npx expo prebuild --platform ios
cd ios && pod install
xcodebuild -workspace EnategaQAPROD.xcworkspace -scheme EnategaQAPROD \
  -configuration Release -sdk iphonesimulator \
  -destination "platform=iOS Simulator,id=<UDID>" \
  -derivedDataPath build/ddata ARCHS=arm64 ONLY_ACTIVE_ARCH=YES \
  CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO build
xcrun simctl install <UDID> build/ddata/Build/Products/Release-iphonesimulator/EnategaQAPROD.app
```

The generated `ios/Podfile` carries a `post_install` hook that rewrites
`Pods/fmt/include/fmt/base.h` to disable fmt's `consteval` path. fmt 11.0.2 (pinned
by react-native 0.79.5) does not compile under Xcode 26's clang without it. `ios/`
is Git-ignored and regenerated by `expo prebuild`, so **this patch is lost on every
prebuild** and must be reapplied (or promoted to an Expo config plugin) — otherwise
the build fails in `CompileC fmt format.cc`.

For an EAS simulator artifact instead:

```sh
npm run build:qa-production:ios
xcrun simctl install booted /absolute/path/to/EnategaQA.app
xcrun simctl launch booted com.enatega.multivendor.qa
```

## Local test data

From `qa-automation`, copy `.env.example` to `.env.mobile.local` and populate:

```dotenv
QA_MOBILE_ENV=production
QA_MOBILE_APP_ID=com.enatega.multivendor.qa
QA_MOBILE_GRAPHQL_URL=https://aws-server-v2.enatega.com/graphql
QA_MOBILE_ALLOWED_HOSTNAMES=aws-server-v2.enatega.com
QA_CUSTOMER_EMAIL=<dedicated-automation-customer>
QA_CUSTOMER_PASSWORD=<secret>
QA_MOBILE_RESTAURANT_ID=<allowlisted-open-restaurant-id>
QA_MOBILE_RESTAURANT_NAME=<exact-visible-name>
QA_MOBILE_PRODUCT_ID=<allowlisted-product-id>
QA_MOBILE_PRODUCT_NAME=<exact-visible-name>
QA_MOBILE_OPTION_ID=<id of one option inside a REQUIRED addon>
QA_MOBILE_CURRENCY=<three-letter-code>
QA_MAX_ORDER_TOTAL=<explicit-positive-ceiling>
# Multi-vendor suite only. Read-only, but it needs a genuine second vendor.
QA_MOBILE_SECOND_RESTAURANT_NAME=<a DIFFERENT allowlisted open restaurant>
QA_MOBILE_SECOND_PRODUCT_ID=<a product on that second restaurant>
```

`QA_MOBILE_PRODUCT_ID` is required by the smoke as well as the production order:
the flow taps the product by its `customer.product.card.<id>` test ID, because the
restaurant menu's scroll container aggregates every child's accessibility label and
a name-based match therefore also matches the whole screen.

The selected product must be in stock and must reach the restaurant minimum after
the scripted quantity increases while remaining below `QA_MAX_ORDER_TOTAL`. It must
also satisfy two structural constraints, or the flow cannot run:

1. **It must open the item screen.** `Restaurant.addToCart` adds straight to the
   cart and never navigates when a food has exactly one variation and no addons.
   Pick a product with multiple variations, or with at least one addon.
2. **It must carry a genuinely required addon** — one whose `quantityMinimum` is at
   least 1. `QA_MOBILE_OPTION_ID` is the id of an *option inside that addon*, not
   the addon id and not the product id.

The scripted quantity ends at 3 units (one increase on the item screen, one in the
cart), so size `QA_MAX_ORDER_TOTAL` against `3 x (base price + required option)`
plus tax.

The local file is Git-ignored. Never place credentials, tokens, or API keys in
tracked YAML or environment templates.

## Safe read-only smoke

```sh
cd qa-automation
npm run mobile:preflight:ios
npm run test:mobile:ios:smoke
npm run report:mobile
```

The smoke reaches checkout and validates pickup, COD, subtotal, tax, and total.
It never receives `QA_PLACE_REAL_ORDER=true` and its flow contains no tap on the
place-order control. Validate twice from clean state before approving the
milestone.

## Read-only P1 regression suite

```sh
npm run test:mobile:ios:regression
```

Runs every flow in `maestro/customer/flows/p1/` (CM-P1-007 … CM-P1-020). They
use the same validated read-only environment as the smoke, so they need no
additional variables and no write guards. None of them taps
`customer.checkout.place-order`.

| Flow | Asserts |
| --- | --- |
| `p1-guest-checkout-gate.yaml` | A guest can browse and fill a cart, but `customer.cart.checkout` is absent until sign-in |
| `p1-search-no-results.yaml` | The empty state and the clear control appear and retract with the query |
| `p1-cart-quantity-and-removal.yaml` | The stepper walks 2→3→1 and the final decrement removes the line |
| `p1-fulfillment-pricing.yaml` | Delivery total ≥ pickup total, and returning to pickup restores the exact figure |
| `p1-session-persistence.yaml` | The session survives a restart, and a cleared install restores the auth wall |
| `p1-account-details.yaml` | The Account screen reports the email and name of the customer that signed in |
| `p1-order-history.yaml` | Current and Past both resolve to real orders or their own empty state; a past order opens a detail with an order number |
| `p1-saved-addresses.yaml` | Addresses resolve to rows or the empty state, and add-address opens the map picker |
| `p1-favourites.yaml` | Favourites open from the hub and hold restaurant cards; with none, the section is absent rather than broken |
| `p1-logout.yaml` | Cancelling the prompt is safe; confirming clears the persisted session, and a restart still lands on the auth wall |
| `p1-checkout-tip.yaml` | A tip of 5 raises the delivery total by exactly 5, and pickup zeroes it and restores the original pickup total |
| `p1-checkout-voucher-invalid.yaml` | An invalid code is rejected, apply-voucher stays offered, and the total is unchanged to the cent |
| `p1-item-configuration.yaml` | Add-to-cart is inert until the required addon is chosen, the stepper will not fall below 1, and the quantity carries into the cart |
| `p1-payment-methods.yaml` | Cash and card are both offered, switching never reprices, and card selection does not leave checkout |

The last nine flows reach screens that carried no test IDs, so `Profile`,
`Account`, `MyOrders`, `Addresses`, `Favourite`, `SelectLocation`, the logout
modal and the checkout tip and voucher modals were instrumented for them. Two controls were left deliberately
uninstrumented so that no flow can reach them by test ID: **Delete Account** on
the Account screen, and the address **edit/delete** modals. Both fire
irreversible mutations on the automation account.

`p1-favourites.yaml` and `p1-order-history.yaml` branch on live data. Each branch
carries its own assertion, so neither can pass on a blank screen — a list that
resolves to nothing must produce that screen's empty state.

## Read-only navigation suite

```sh
npm run test:mobile:ios:navigation
```

Runs `maestro/customer/flows/p3/` (CM-P3-001 … CM-P3-004). It answers one
question: does every reachable button and icon land on the screen it claims to,
and can the customer get back out? It reuses the smoke environment exactly, so it
needs no extra variables and no write guards, and it never taps
`customer.checkout.place-order`.

| Flow | Asserts |
| --- | --- |
| `p3-tab-navigation.yaml` | All five tab icons land on their own screen; Restaurants and Store share one component and must genuinely swap; a signed-in customer never lands on the auth wall |
| `p3-profile-hub-navigation.yaml` | Every Profile hub row opens its destination **and pops back to the hub** — Account, Addresses, Order history, Active orders, Support, FAQ, and Favourites when present |
| `p3-catalog-navigation.yaml` | A restaurant card opens the loaded restaurant, a product card opens the item, and each pops back to the screen that pushed it rather than to the tab root |
| `p3-cart-checkout-navigation.yaml` | Instructions, tip and voucher modals each open **and dismiss**; fulfillment and payment switch without navigating away; leaving checkout returns to an intact cart |

Every destination is asserted by a screen-level test ID rather than by visible
text, so a flow cannot pass on a spinner or on a screen that merely looks right.
`customer.restaurant.screen` marks the loaded restaurant render specifically, not
the loading skeleton that shares its markup.

These flows needed screen markers that did not exist, so `Main`, `Menu`,
`SearchScreen`, `Restaurant`, `Help` and `CustomerSupport` were instrumented, plus
the restaurant screen's own back control (`customer.restaurant.back`), which is a
custom `ImageHeader` button rather than the stack header. The instrumentation is
additive test IDs only — no behaviour changed.

Two navigation controls remain deliberately unreachable, as before: **Delete
Account** and the address **edit/delete** modals. This suite does not look for
them by test ID or by text.

### Popping a stack screen

`maestro/customer/subflows/back.yaml` taps the header's `Go back` accessibility
label. Maestro's own `back` command is a no-op on the iOS simulator, and
`headerBackImage` sits inside React Navigation's pressable, so there is no test ID
to add without replacing the header. Like the native Alert's `Cancel`/`OK` in the
multi-vendor flow, that label is English — localising the app means localising
this string. The restaurant screen is the exception and uses
`customer.restaurant.back`.

## Multi-vendor suite (extra fixtures)

```sh
npm run test:mobile:ios:multi-vendor
```

Runs `maestro/customer/flows/p2/` (CM-P2-001). Still read-only and still without
write guards, but it needs a second allowlisted restaurant and product, which is
why it is not part of `test:mobile:ios:regression`. The runner rejects the run if
the second restaurant name or product ID matches the first — a cart shared by one
vendor with itself proves nothing.

| Flow | Asserts |
| --- | --- |
| `p2-cross-restaurant-cart.yaml` | Adding from a second restaurant prompts before replacing the cart: declining preserves the original line, accepting empties it |

The prompt is a native `Alert`, so it is matched by its `Cancel` and `OK` button
text rather than by a test ID. If the app's alert button labels are localised
away from English, this flow needs the localised strings.

Every flow in both suites starts from `launch.yaml` with `clearState: true` and
none depends on state left by another, so they are order-independent and
Maestro's `continueOnFailure: false` is the only thing that stops a run early.
That also covers `p1-logout.yaml`, which ends the shared automation account's
session: the next flow signs in again from a cleared install.

To iterate on a single flow, run Maestro directly with the same variables the
runner passes (`APP_ID`, `CUSTOMER_EMAIL`, `CUSTOMER_PASSWORD`, `RESTAURANT_NAME`,
`PRODUCT_NAME`, `PRODUCT_ID`, `OPTION_ID`, `CURRENCY`, `MAX_ORDER_TOTAL`, plus
`SECOND_RESTAURANT_NAME` and `SECOND_PRODUCT_ID` for the P2 flows); the
exact argument list for the last run is recorded in
`reports/maestro/<run-id>/command-metadata.json`.

## Manual production order and cancellation

This is never called by push, pull-request, nightly, or scheduled workflows.
Set all guards only for the single approved invocation:

```sh
QA_MOBILE_ALLOW_PRODUCTION_WRITES=true \
QA_PLACE_REAL_ORDER=true \
QA_MOBILE_FULFILLMENT=pickup \
QA_MOBILE_PAYMENT_METHOD=COD \
QA_RUN_ID="mobile-$(date +%Y%m%d-%H%M)-approved" \
npm run test:mobile:ios:production-order
```

The order instructions contain `QA-RUN-<Run ID>`. If the command fails after
placing the order, do not rerun it. Locate that Run ID/order number in Store or
Admin, cancel it manually, and retain the entire report directory as evidence.

JUnit, HTML, screenshots, Maestro debug output, and non-secret command metadata
are retained below `reports/maestro/<run-id>/`.
